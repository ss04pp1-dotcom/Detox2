# r9.3 (v2.5.3 / versionCode 18) — Lock My Phone schedules + a start-button bug

Item 1 of the audit's priority list (`docs/SOCIAL-SENTRY-PARITY-AUDIT.md`,
section E). Built on r9.2.

## Fixed: Lock My Phone could not be started from the UI
`NativeBridge.isDeviceAdminActive()` (Dart) read `r.data['active']`, but the
native side replies with `adminActive`. The Lock My Phone screen therefore
always believed Device Admin was OFF, so the "Lock it down" button and the
duration chips were permanently disabled (the Account screen's admin toggle
had the same wrong reading). Dart now reads `adminActive`.

## Fixed: lists of objects broke the MethodChannel boundary
`jsonToMap` only converted the top level; a JSON array containing objects kept
raw `org.json.JSONObject` elements (and `JSONObject.NULL`), which the standard
message codec cannot serialize. Conversion is now recursive.

## New: scheduled + recurring Lock My Phone windows
Social Sentry LMP parity ("one-shot scheduled" + "regular schedules").

- **Weekly**: pick days (Mon..Sun) + start/end time. End earlier than start
  runs past midnight; start == end locks all day. Minimum window 15 min.
- **One-time**: date + time + duration (30 min .. 8 h).
- Native `LockScheduler` (persisted in SharedPreferences) + `AlarmManager`
  alarm (exact when the exact-alarm permission is granted, otherwise
  inexact/allow-while-idle) + `LockScheduleReceiver`; also re-evaluated on
  app start, boot, TIME_SET / TIMEZONE_CHANGED, every guard-job pass and
  engine 2's slow tick, so a missed or wiped alarm never loses a window.
- When a window is live it starts an ordinary lock-my-phone session for the
  REMAINING window, so every existing rule applies (1.5 s lock loop, call
  mode, guards, coin bailout as the only exit). A window that continues after
  another session ends is chained via an alarm at that session's end.
- Gates identical to a manual start: Commitment Pact accepted + Device Admin
  active; otherwise nothing starts.
- Safeguards: a schedule cannot be edited, disabled or deleted while its
  window is live and a session is running (that would be a free exit); a
  schedule created or edited inside an already-running window starts from its
  NEXT window (no surprise instant lock); if the user pays the bailout, the
  same window is not re-locked.
- Bridge: `getLockSchedules`, `saveLockSchedule`, `deleteLockSchedule`.
  UI: "Scheduled locks" section on the Lock My Phone screen
  (`lock_schedules_section.dart`).

Balanced brackets (Kotlin + Dart), 94 Dart -> Kotlin methods all handled,
imports resolve, manifest components resolve, XML well-formed, and the
